Where I started, and where this took me

Completing the Computer Science program and developing this ePortfolio helped me reflect on my growth as a student, a developer, and a technology professional. When I first built many of these projects, my main goal was to meet the course requirements and make the applications work correctly. Through the capstone, I learned to go back through that earlier work, review it more critically, and improve it from a professional software-development perspective.

That process pushed me to focus on the things that matter beyond a class deadline: security, maintainability, code organization, database design, input validation, documentation, and user-centered design. It also showed me how the areas of computer science connect. Software engineering, algorithms, data structures, databases, and security are not separate skills. In real applications they work together to produce systems that are reliable, useful, and safe.

My professional background and career goals center on automation, controls engineering, digital solutions, and cybersecurity. Because of that, I wanted this portfolio to show projects that map to real-world technology needs. In industrial and business settings, software is used to collect data, display information, support decisions, and protect critical systems. The artifacts here demonstrate my ability to build and improve applications with those goals in mind.

Collaborating in a team environment

Much of the program treated software as a team sport rather than a solo exercise. In my software-development-lifecycle coursework I worked inside an Agile and Scrum framework: writing user stories, breaking work into sprints, and tracking progress against a backlog. That experience changed how I scope a project. Instead of trying to build everything at once, I learned to deliver a working increment, gather feedback, and iterate, which is exactly the pattern I followed in this capstone by enhancing each artifact one milestone at a time.

The capstone itself was built around collaboration with an audience. My code review was prepared for peers and a manager, and the milestone narratives were written so another developer could pick up the work, understand the reasoning, and continue it. Working in version control reinforced the same habit: a clean commit history and a clear README are how a team stays in sync. In my target field, controls and automation projects are commissioned by cross-functional teams of engineers, technicians, and operators, so building software that others can read, run, and extend is not optional.

Communicating with stakeholders

I came to see communication as a deliverable, not an afterthought. Across the program I practiced translating technical decisions into language a non-specialist stakeholder can act on, whether through design documents, README files, inline comments, or a recorded code-review walkthrough. The informal code review for this portfolio is a direct example: I had to explain how existing code worked and justify each planned enhancement to an audience that was not living inside the codebase with me.

My database artifact sharpened this further. A dashboard exists to help someone make a decision, so I had to think about what a user actually needs to see and how to keep the interface honest and easy to read. Writing setup instructions that a stranger could follow forced me to communicate precisely: if the steps are vague, the project does not run. That discipline carries straight into industrial work, where an HMI or reporting dashboard has to give operators clear, trustworthy visibility into a process.

Data structures and algorithms

The program gave me a working command of core data structures and the algorithms that operate on them. In my data-structures-and-algorithms course I implemented and compared structures such as vectors, hash tables, and binary search trees, and reasoned about the trade-offs between them, including how the choice of structure changes the time complexity of searching, inserting, and sorting. That habit of weighing trade-offs rather than reaching for the first structure that works is something I now apply by default.

My algorithms artifact, a C++ and OpenGL 3D scene, is where I show this in practice. The scene stores texture data in a fixed-size array and makes structured rendering decisions every frame, so the enhancements were genuinely algorithmic: I corrected faulty projection logic, added boundary checking so the program cannot overrun its texture array, and fixed resource cleanup so handles are released correctly. These are small changes with real consequences for correctness, stability, and memory safety.

Software engineering and databases

On the engineering side, the program moved me from "make it run" to "make it maintainable." A software-testing-and-QA course taught me to think about correctness systematically, writing unit tests and considering edge cases before assuming code was done. I applied that mindset to my mobile artifact by pulling scattered logic into dedicated, single-responsibility classes, a centralized validator and a password utility, so the rules live in one place and the rest of the app simply calls them. Separating responsibilities made the code easier to read, test, and hand off.

On the database side, my SQL coursework and client-server development course gave me the foundation to work across both relational and document databases. In this portfolio I work with SQLite on the mobile app and MongoDB on the dashboard. The database enhancement is where I am proudest of the engineering: I moved configuration out of source code and into environment variables, added indexes and field projections so queries return only what the dashboard needs, added paging so the app does not load every record at once, and pushed the breed-distribution calculation into a MongoDB aggregation pipeline so the work happens on the server instead of the client. Those are the trade-off decisions, what belongs in the database versus the application, that define real database engineering.

Security mindset

Security is the thread that runs through everything I value as a soon-to-be professional, and it connects directly to my interest in cybersecurity. A software-security course introduced me to secure coding practices and to looking at my own code the way an adversary would, asking where input is trusted that should not be and where sensitive data is exposed. I carried that lens into every artifact in this portfolio.

In the mobile app I replaced unsafe password handling with salted PBKDF2 hashing, so a raw password is never stored. In the dashboard I removed hardcoded database credentials, moved secrets into a private .env file protected by .gitignore, added password generation and rotation tooling, ran the app under a least-privilege database account, and restricted the interface to a set of approved query filters instead of accepting raw user input. In the graphics project, defensive programming, boundary checks and safe cleanup, is its own form of security. The common idea is to anticipate misuse and design it out before it becomes a vulnerability.

How my artifacts fit together

The three artifacts are deliberately different in language and platform, Java and SQLite on Android, C++ and OpenGL on the desktop, and Python with MongoDB on the web, because together they show range rather than a single trick. But they are bound by a consistent engineering point of view. Each one began as coursework that worked, and each was re-engineered to be more secure, more maintainable, and closer to something I would be comfortable shipping.

Read as a set, they trace the path I want my career to take. The mobile app shows I can build organized, secure software around a user's goal. The graphics project shows I can read unfamiliar code, reason about data structures and resources, and make precise corrections without breaking a complex system. The dashboard shows I can connect software to a database and turn raw records into decisions, while treating credentials and data with the care a production system demands. That combination, building it, hardening it, and presenting the data clearly, is exactly what automation, controls, and cybersecurity work asks for. The detailed artifacts that follow are the evidence behind every claim I have made here.
