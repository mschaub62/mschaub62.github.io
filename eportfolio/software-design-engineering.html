The artifact

The software design and engineering artifact is a weight-tracking app originally created in Android Studio using Java. The app lets a user create an account, log in, add a weight, update and delete records, save a goal weight, and optionally enable SMS notifications. It uses SQLite to store user records, weight history, goal-weight information, and local settings.

Why it's included

I selected this artifact because it is a working application with a clear purpose, not just a small code sample. It includes screens, user interaction, persistent storage, and logic that connects a user's goal to the app's behavior. That makes it a good example of building software around a real user need, and it lets me show mobile development, Java, database use, validation, and secure-coding improvements in one place.

What changed in the enhancement

The most important change was safer password handling. The original version handled passwords in a way that was not safe for a real application. The enhanced version adds a PasswordUtils class that uses salted PBKDF2 hashing, so the raw password is never stored in the database. User account information should be treated as private, even in a class project.

I also added centralized validation through a WeightValidator class. Instead of scattering input rules across the project, the rules for usernames, passwords, phone numbers, and weight values now live in one place. The app checks for reasonable weight ranges and stronger password requirements, which improves data quality and makes the app less likely to accept bad input.

Finally, I improved the goal-weight logic and the safety of the app. The goal feature now uses the logged-in user's ID when reading the saved goal, so the goal stays tied to the correct user. I added a delete confirmation before a weight entry is removed, because weight history is user-created data and deleting it by accident would be frustrating. The SMS feature was made optional and permission-based: if the user does not grant SMS permission, the app keeps working for its main purpose of tracking weight.

Before: passwords compared as stored text — exposed if the database were ever read.
After: a per-user random salt and 120,000 PBKDF2 iterations. The app stores only the salt and the derived hash, and verifies by re-deriving and comparing.

public static PasswordRecord hashPassword(String password) {
    byte[] salt = new byte[SALT_BYTES];
    new SecureRandom().nextBytes(salt);   // unique salt per user
    byte[] hash = deriveHash(password, salt);
    return new PasswordRecord(toHex(hash), toHex(salt));
}

public static boolean verifyPassword(String password, String storedHash, String storedSalt) {
    byte[] actualHash = deriveHash(password, fromHex(storedSalt));
    return Arrays.equals(fromHex(storedHash), actualHash);
}

Reflection

Reviewing a project I had already finished taught me that the original app had its main features working, but a closer read revealed places where the design could be stronger, especially around security. That is a good stepping stone, because I am now looking at my work as a soon-to-be professional who has to think about optimizing designs and writing more secure programs.

Part of the learning was reading the code from another developer's point of view: how would someone else debug this? That is when it became clear that separating responsibilities, by adding helper classes for password handling and validation, would make the project cleaner and easier to understand.

Updating my original plan honestly: I did not complete the full Room and ViewModel (MVVM) conversion for this milestone. Instead I focused on practical changes that improved the app while keeping it stable, repository-style organization, stronger validation, password hashing, safer delete behavior, and corrected goal logic. A full Room and MVVM structure is still a good future improvement, but the current work was a solid step forward.
