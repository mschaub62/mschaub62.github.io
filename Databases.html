The artifact

The database artifact is my CS-340 Grazioso Salvare animal-shelter dashboard, built with Python, MongoDB, PyMongo, Dash, Plotly, and Dash Leaflet. It connects to the Austin Animal Center outcomes data and lets a user filter animal records by rescue profile. The dashboard then shows the records in a table, draws a breed chart, and updates a map based on the selected animal.

Why it's included

I selected this artifact because it is a working database application, not a small script. It shows a program connecting to a database, retrieving and filtering records, and presenting results in a way that helps a user make a decision. The value of the project comes from the MongoDB data and how the dashboard uses it, which makes it a strong database example. It also fits my career goals in automation and digital solutions, where industrial systems rely on dashboards, databases, and reporting tools to give teams better visibility.

What changed in the enhancement

A stronger, safer connection layer. The original dashboard worked, but it used hardcoded database credentials and pulled more data than it needed. The enhanced version loads the MongoDB username, password, host, database, and collection from environment variables and a local .env file, so the password is never written into the Python source. That matters because this artifact may be published to GitHub as part of my portfolio, and credentials should never be exposed in a public project.

Better password management. I added a setup script that prompts for the dashboard password using hidden input, and can generate a strong random password if the user prefers. A separate rotation script lets the password be changed later without hunting through the program. The dashboard runs under a limited MongoDB user scoped to the aac database rather than a broad admin account, and a .gitignore keeps the local .env out of version control.

More efficient, safer queries. The enhanced version uses pre-approved rescue-profile filters instead of accepting raw query input, so the user can only choose from known options. I added projections so only the fields needed for the table, chart, and map come back; paging so the dashboard does not load every record at once; and indexes on the fields used most in the filters. The breed chart now runs as a MongoDB aggregation pipeline, grouping and counting breeds on the server before results reach the dashboard.

ENHANCED · server-side aggregation 
pipeline = [
    {"$match":   dict(query)},
    {"$group":   {"_id": "$breed", "count": {"$sum": 1}}},
    {"$sort":    {"count": -1, "_id": 1}},
    {"$limit":   max(1, min(int(limit), 25))},
    {"$project": {"_id": 0, "breed": "$_id", "count": 1}},
]
return list(self.collection.aggregate(pipeline))

Reflection

This process taught me that a program can work for a class project and still need real changes before it is ready to show as a professional artifact. When I first built the dashboard, my goal was to connect to MongoDB and make the table, chart, and map work. Reviewing it now, I had to think like a soon-to-be professional: what happens if another person runs this, if the dataset grows, or if the project is uploaded to GitHub with private information still inside it?

I ended up doing more security work than I originally planned. My first plan focused on environment variables, projections, indexes, approved filters, and aggregation. As I worked, I realized password management was one of the most important improvements, precisely because this artifact could be viewed in a public setting. The hardest part was making the dashboard more secure while keeping it easy to run locally, which meant writing clear setup instructions, and improving the database layer without changing the project's purpose. I kept the original rescue-profile idea, table, chart, and map, and improved how the project connects to and uses the database.
